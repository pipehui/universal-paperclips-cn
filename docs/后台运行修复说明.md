# 后台运行修复说明

[返回项目首页](../README.md)

本文记录 **2026-10-05** 的后台运行修复。目标是让打开中的游戏页面在切换标签页后继续推进，并在定时回调延迟或页面冻结恢复后补回尚未计算的时间。

## 1. 原来的问题

原实现存在三类计时依赖：

| 原有机制 | 后台运行时的影响 |
| --- | --- |
| 生产等逻辑使用 `setInterval(..., 10)`，销售等逻辑使用 `setInterval(..., 100)`；每次回调只推进一步 | 回调被延迟后，没有依据实际经过的时间补算，游戏速度随回调频率下降 |
| 投资汇总、自动锦标赛和终局计时混在 `requestAnimationFrame()` 驱动的刷新逻辑中 | 页面停止绘制时，这些游戏状态更新也会停止 |
| 锦标赛使用独立的 `setTimeout()`，战斗使用独立的 16ms `setInterval()` | 即使修复生产循环，这两个系统仍可能因后台降频而变慢 |

浏览器会对隐藏页面的定时器进行节流，并通常暂停后台页面的动画帧回调；具体策略取决于浏览器和运行条件。相关机制见 [Chrome 后台定时器说明](https://developer.chrome.com/blog/timer-throttling-in-chrome-88/)及 [MDN 页面可见性说明](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)。

修复前的确定性复现：模拟后台每秒仅触发一次定时回调，经过 10 秒后，生产循环只执行 **10 次**，而按原定 10ms 步长应执行 **1000 次**。因此，用户看到的“暂停”也可能是进度大幅变慢。

## 2. 共享游戏时钟与后台唤醒

新增 [GameClock.js](../public/GameClock.js)，统一管理游戏逻辑的执行时间。每次被唤醒时，它通过 `performance.now()` 计算经过的时间，再判断哪些模拟步骤已经到期。

例如，生产步长为 10ms，即使一次回调间隔了 1 秒，也会产生约 100 个待执行的生产步骤。销售、战斗和事件同样按各自步长推进。

当前有三个唤醒来源：

| 来源 | 配置 | 作用 |
| --- | --- | --- |
| 页面定时器 | 请求每 10ms 唤醒一次 | 前台日常调度，以及 Worker 不可用时的回退路径 |
| [GameClockWorker.js](../public/GameClockWorker.js) | 请求每 50ms 发送一次消息 | 帮助后台页面持续获得执行机会，减轻对页面定时器的依赖 |
| `visibilitychange` | 页面可见性发生变化时 | 切换回来时主动检查并处理待补算时间 |

这些间隔是请求的调度频率，实际执行仍受浏览器调度影响。**Worker 只发送唤醒消息；游戏状态、生产计算和 DOM 操作仍在主线程中执行。** 多个来源唤醒同一个时钟，不会各自重复增加进度。

如果 Worker 创建失败或脚本加载失败，页面定时器与时间补算仍可使用，但后台实时追赶能力可能下降。Worker 也不能保证页面在所有节能或冻结策略下始终运行。

## 3. 按时间顺序补算，并限制每批工作量

时钟分别记录已经模拟到的时间和需要追赶到的目标时间，并从所有任务中选择最早到期的一个执行。生产、销售、锦标赛和战斗会按模拟时间交错推进，避免先补完全部生产、再统一处理销售等顺序变化。

补算过程中创建的新延时任务，以**当前正在回放的模拟时间**为起点。例如，锦标赛的一个回合在补算时创建下一个 50ms 延时，下一个回合仍可以在同一段积压时间内继续推进。

为了让页面有机会处理输入和绘制，每批在满足以下任一条件后让出主线程：

- 已执行 **1000 个调度回调**。
- 本批耗时达到约 **8ms**。

这里的 1000 次是所有循环的调度回调总数；一个回调内部可能执行多个游戏函数。耗时检查发生在回调结束后，因此单个耗时较长的回调仍可能超过 8ms。

未完成的步骤会保留到后续批次，当前实现没有按固定分钟数截断积压时间。离开越久、游戏阶段越复杂，恢复时完成补算所需的时间也可能越长。

## 4. 各个游戏系统的调整

游戏循环现在分为以下几类：

| 循环 | 模拟步长或触发方式 | 主要工作 |
| --- | --- | --- |
| `fast` | 10ms | 生产、运算、创造力、无人机和探测器等原有快速逻辑 |
| `slow` | 100ms | 销售、金属丝价格、项目检查和投资交易调度；自动保存仍每 250 个慢循环触发一次，即约 25 秒模拟时间 |
| `events` | `1000 / 60` ms，固定 60Hz | 投资汇总、策略选择同步、游戏标志、自动锦标赛启动和终局事件 |
| `combat` | 16ms | 飞船移动、战斗计算与战斗结束判断 |
| `render` | `requestAnimationFrame()` | 统计显示、按钮状态和终局界面等画面更新 |

**生产与销售。** 保留原有 10ms、100ms 步长和计算函数，由共享时钟决定需要执行多少步。普通 `Loop` 在配置了 `clock` 时使用共享调度，未配置时仍可使用原生定时器。

**投资与游戏标志。** 从画面刷新函数中提取 `updateInvestmentValues()` 和 `updateGameFlags()`。投资风险设置、证券总值、投资组合总值，以及相关解锁标志和探测器信任分配汇总，都能在没有绘制帧时更新。

**自动锦标赛。** 新增 `updateAutoTourney()`，将启动等待移到固定 60Hz 的事件循环。启动条件依据锦标赛结果、自动运行状态和运算资源判断，移除了对结果表格 CSS 显示状态的依赖。回合之间两处 50ms 延时改用 `Paperclips.game.clock.setTimeout()`，支持连续回合的时间补算。原来按 300 个绘制帧等待的启动计时，现在约为 5 秒模拟时间，不再随显示器刷新率变化。

**太空战斗。** 将原先独立的 16ms 定时器改为注册到共享时钟的 `combat` 循环。页面隐藏时跳过画布清空及飞船、爆炸绘制，继续执行移动和战斗计算。

**终局流程。** 计时递增、金属丝返还和阶段消息移到事件循环；面板隐藏、数值显示等保留在渲染循环。这样后台仍能推进终局，界面重绘也不会重复返还金属丝。

在补充终局验证时，同时修正了两个原有错误：

- `incrementEndTimer()` 原来递增 `timer1` 等错误变量，现改为实际使用及保存的 `endTimer1` 等变量。
- `endTimerIs()` 原来在计时恰好相等时跳过回调，现改为仅在等于指定值时执行，保证各个指定时刻正确触发。

## 6. 验证结果与复现方法

在项目根目录运行：

```bash
npm test
```

2026-10-05 验证结果：**96 个项目、94 条项目消息的本地化检查通过，14 个游戏脚本语法检查通过，14 项回归测试全部通过。** 回归测试使用 Node.js 内置测试工具，无需安装额外测试依赖。

| 回归场景 | 检查内容 |
| --- | --- |
| 后台回调降至每秒一次 | 模拟 10 秒仍执行 1000 次生产和 100 次销售回调 |
| 前台与延迟回调对比 | 每 10ms 唤醒与积压 60 秒后集中唤醒，产生相同的模拟步骤顺序 |
| 一小时暂停后恢复 | 首批执行会让出主线程，最终补足 360000 次快速循环；重复可见性通知不重复计时 |
| 重复启动与主动暂停 | 重复 `start()` 不增加重复调度；`stop()` 期间不累计进度 |
| 嵌套延时 | 连续十个 50ms 延时按模拟时间依次触发 |
| 自定义循环与调速 | 战斗步长、快速循环调速及任务取消正常 |
| 实际生产函数 | 测试产能为每秒 100 个时，模拟 10 秒生产 1000 个回形针，金属丝相应减少 |
| 投资与自动锦标赛 | 无绘制帧时仍更新投资总值；结果表格隐藏也能按条件启动自动锦标赛 |
| Worker 与页面定时器共同唤醒 | 同一段时间只计算一次，停止时终止 Worker |
| Worker 创建失败 | 页面定时器仍可驱动补算 |
| Worker 加载失败 | 终止失败 Worker 后，页面定时器仍可驱动补算 |
| 实际锦标赛函数 | 回合延时能在补算期间依次执行，完成比赛并产生结果 |
| 实际终局事件链 | 隐藏状态下按指定时刻返还共 10 单位金属丝，重绘不会重复发放 |
| 实际战斗函数 | 画布隐藏时，160ms 模拟时间仍推进 10 个战斗步骤 |

上述“60 秒积压”“一小时暂停”等自动化场景使用可控时钟模拟，验证计时与补算逻辑，不等同于真实挂机同样时长。

开发期间还在 **Windows Chrome、本地 HTTP 页面**上进行了额外浏览器验证；这些检查独立于 `npm test`：

| 浏览器场景 | 当次记录 |
| --- | --- |
| 切到另一个标签页，并确认 `document.hidden === true` | 约 5.020 秒推进 501 次快速计算，接近正常的每秒 100 次 |
| 通过浏览器调试协议冻结页面约 3 秒后恢复 | 观测区间约 3.141 秒，恢复后累计推进 314 次快速计算 |
| 人为注入 60 秒待补算时间 | 首批只执行部分步骤，后续分批补足；计算期间正常经过的时间也继续计入 |

这些浏览器检查通过，未捕获到游戏 JavaScript 执行错误。当前没有完成其他浏览器、移动端或长时间真实挂机的验证。

手动检查可以按以下步骤进行：

1. 运行 `npm start`，打开游戏，准备已经能自动生产且金属丝充足的存档。
2. 记录回形针总数与大致生产速度，切到其他标签页等待一段时间。
3. 返回游戏，观察总数是否继续增长；长时间离开后允许补算分批完成。
4. 如已解锁自动锦标赛或太空战斗，可分别检查比赛与战斗状态是否推进。市场价格、随机事件和资源耗尽会影响实际收益，收益不一定是离开前速度的简单倍数。

## 7. 兼容性、限制与发布

- **存档格式沿用原实现。** 本次未修改存档字段及导入导出格式，也未增加运行时第三方依赖。
- **适用范围是保持打开的页面。** 普通后台切换时尝试持续推进；彻底冻结时，等待页面恢复执行后补算。
- **不包含跨关闭的离线收益。** 关闭、刷新或被浏览器丢弃后重载，会按原有逻辑读取已保存进度；本次没有保存用于跨页面生命周期结算的时间戳。
- **主动暂停仍然有效。** 调用 `Paperclips.game.stop()` 会停止唤醒来源，暂停期间不计入游戏进度；这不是新增的界面暂停按钮。
- **后台计算会继续使用 CPU 和电量。** 本次减少了隐藏战斗画布的绘制，但原有部分逻辑仍包含 DOM 操作，尚未完成全面的逻辑与渲染分离。
- **不同环境仍可能有差异。** Worker 不可用时可以回退，但更依赖恢复后的补算；系统休眠、进程终止及移动端节能场景未在本次验证中覆盖。

当前 README 提供本地启动方式，已移除在线游玩入口。仓库保留原有 GitHub Pages 部署流程；如需自行部署，应在目标站点与浏览器中重新验证后台运行行为。
